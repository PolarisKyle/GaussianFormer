# GaussianFormer 多机多卡训练改造总结（DDP）

## 1. 问题定义与目标

本次改造的目标不是“仅支持单机多卡”，而是统一支持以下两类场景，并保持训练主流程基本不变：

1. **多机多卡（推荐）**：通过 `torchrun` 启动，依赖环境变量自动完成全局进程编排。  
2. **单机多卡（兼容）**：当未使用 `torchrun` 且本机有多卡时，继续使用 `torch.multiprocessing.spawn`。

核心目标：

- 训练脚本可在不同部署方式下自动选择分布式初始化路径；
- 不破坏原有单卡训练行为；
- 避免多进程重复写日志、重复写 checkpoint；
- 保持 DDP 与数据采样、SyncBN、保存恢复逻辑一致可用。

---

## 2. 设计思路（先判定启动模式，再统一训练语义）

整体思路是：**把“如何启动进程”与“训练时的分布式语义”解耦**。

### 2.1 启动模式判定

在 `train.py` 中优先根据环境变量判断是否为 `torchrun` 场景：

- 若 `WORLD_SIZE > 1`，走 `torchrun/env://` 初始化；
- 否则若 `args.gpus > 1`，走单机 `spawn + tcp://` 初始化；
- 否则走单卡非分布式。

这样做的原因是：

- 多机场景下，`torchrun` 已经为每个进程分配好 `RANK/LOCAL_RANK/WORLD_SIZE`，最稳妥的做法是直接复用；
- 单机场景继续保留历史行为，避免影响已有脚本。

### 2.2 统一训练语义

不论是 `torchrun` 还是 `spawn`，最终都收敛到一致的运行时语义：

- `distributed` 布尔值；
- `world_size`（总进程数）；
- `rank`（全局进程编号）；
- `local_rank`（当前节点内 GPU 编号）。

后续模型封装、DataLoader、日志与保存逻辑都只依赖这组语义，不关心具体启动方式。

---

## 3. 具体改动点

## 3.1 `init_distributed(local_rank, args)`：双路径初始化

该函数实现了三分支：

1. **多机/torchrun 分支（`WORLD_SIZE > 1`）**
   - 从环境变量读取 `LOCAL_RANK`；
   - `torch.cuda.set_device(local_rank)` 绑定当前进程 GPU；
   - `dist.init_process_group(backend="nccl", init_method="env://")` 初始化。

2. **单机多卡/spawn 分支（`args.gpus > 1`）**
   - `rank = local_rank`，`world_size = args.gpus`；
   - 使用 `MASTER_ADDR` 与 `MASTER_PORT` 组装 `tcp://` 初始化地址；
   - 初始化后设置当前 CUDA 设备。

3. **单卡分支**
   - 不初始化进程组，按普通训练执行。

价值：通过一个函数把模式差异收敛，主流程无需散落判断。

## 3.2 入口逻辑：优先 torchrun，回退 spawn

在 `if __name__ == "__main__"` 中：

- 当检测到 `torchrun`（`WORLD_SIZE > 1` 且存在 `LOCAL_RANK`）时，直接调用 `main(LOCAL_RANK, args)`；
- 否则按旧逻辑：
  - 多卡：`torch.multiprocessing.spawn(main, ...)`
  - 单卡：`main(0, args)`。

价值：兼容历史使用习惯，同时新增多机能力。

## 3.3 DDP 封装与 SyncBN

在 `distributed=True` 时：

- 可选执行 `SyncBatchNorm.convert_sync_batchnorm`；
- 使用 `DistributedDataParallel` 包装模型，`device_ids=[torch.cuda.current_device()]`；
- `find_unused_parameters` 由配置项控制。

价值：保证多卡统计一致性，并允许复杂分支模型按需开启未使用参数检查。

## 3.4 DataLoader 与 DistributedSampler 对齐

`get_dataloader(..., dist=distributed)` 在分布式场景下使用分布式采样器，并在每个 epoch 调用 `sampler.set_epoch(epoch)`。

价值：确保各 rank 数据切分不重叠且每轮 shuffle 一致，避免样本重复与训练偏差。

## 3.5 仅 Rank0 执行副作用操作

将以下操作约束为 `rank == 0`：

- 创建工作目录、导出配置；
- TensorBoard 与日志核心输出；
- 周期性保存 checkpoint 与软链接更新；
- 大多数训练阶段可读日志打印。

价值：避免多进程并发写文件/写日志导致冲突与噪声。

## 3.6 训练结束清理

在分布式场景且进程组已初始化时执行 `dist.destroy_process_group()`。

价值：避免资源泄漏，保证多次任务启动稳定。

---

## 4. 为什么这样改（关键取舍）

1. **优先 `torchrun + env://`**  
   这是 PyTorch 官方推荐的多机 DDP 方式，进程拓扑由启动器统一管理，脚本内部只消费标准环境变量，耦合最低。

2. **保留 `spawn` 分支**  
   兼容现有单机多卡用户，不强制改造所有旧启动脚本。

3. **统一到 `rank/world_size/local_rank` 三元语义**  
   让训练主流程只关注“我是哪个进程、该用哪张卡、总共有多少进程”，减少分支散落与维护成本。

4. **严格 Rank0 副作用**  
   是工程稳定性的关键，否则在多机多进程下会出现重复写盘、日志交错甚至 checkpoint 覆盖。

## 5. 运行与使用建议

## 5.1 多机多卡（推荐）

在每台机器执行（示意）：

```bash
torchrun \
  --nnodes=2 \
  --nproc_per_node=8 \
  --node_rank=${NODE_RANK} \
  --master_addr=${MASTER_ADDR} \
  --master_port=${MASTER_PORT} \
  train.py --py-config config/xxx.py --work-dir out/xxx
```

要求：

- 所有节点代码与环境一致；
- `MASTER_ADDR/MASTER_PORT` 全节点可达；
- 每节点 `nproc_per_node` 与可用 GPU 数一致；
- 数据路径在各节点可访问（本地同构或共享存储）。

## 5.2 单机多卡（兼容）

不使用 `torchrun` 时，脚本会自动走 `spawn`：

```bash
python train.py --py-config config/xxx.py --work-dir out/xxx
```

---

## 6. 边界条件与风险点

1. **环境变量不完整**：多机下若 `torchrun` 参数不一致，会导致进程组初始化阻塞。  
2. **端口冲突**：`MASTER_PORT` 被占用会初始化失败。  
3. **数据不可达**：某些节点读不到数据会造成训练 hang 或报错。  
4. **配置与显存不匹配**：多机扩展后全局 batch 变化，需同步检查学习率与梯度累积策略。  
5. **Checkpoint 恢复一致性**：恢复时需确保各进程加载同一 checkpoint，且仅 Rank0 负责写入。

---

## 7. 一句话总结

本次多机多卡改造的本质是：**以 `torchrun/env://` 为主路径建立标准 DDP 初始化，保留单机 `spawn` 兼容路径，并通过统一 rank 语义与 Rank0 副作用约束，保证训练行为在不同部署形态下稳定一致。**
